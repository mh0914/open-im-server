# OpenIM 全量修改方案（总体版）

## 1. 结论

需要重新生成修改方案。

原因不是前一版方案有错误，而是范围不够。现有文档 [openim-chatroom-modification-plan-zh_CN.md](./openim-chatroom-modification-plan-zh_CN.md) 只覆盖了“如何把原生群组改造成聊天室”这一条主线，没有把以下内容完整纳入：

1. 所有消息类型的产品化落地。
2. `open-im-server`、`chat-main`、`openim-electron-demo` 三层分别要改什么。
3. 登录注册、通知体系、自定义消息、提示消息、系统通知的完整改造范围。
4. 本地开发版与服务器互联网版的配置、部署、测试、文档和分支策略。

因此，本文件作为新的“总体修改方案”使用，旧的聊天室方案继续保留，但降级为本方案的一个专题子文档。

## 2. 基线版本

当前三个仓库已经打上统一基线标签：

- Tag 名称：`im-native-version`
- Tag 说明：`IM原生版本`

对应提交如下：

- `open-im-server`：`229138f49a82ab2d884fbe35c60dfd22c5ed04c3`
- `chat-main`：`df6ce24c3ae2e1666a08cc81f53e6d7c103ac987`

分支职责如下：

- `main`
  - 面向服务器部署和互联网接入
- `dev`
  - 面向本地 Docker 部署和本地客户端测试

## 3. 总体改造目标

目标不是只做“能聊天”，而是把当前原生 OpenIM 项目逐步改造成符合你需求清单的产品版本。

本次总体改造建议分为三层：

1. 内核能力层：`open-im-server`
2. 业务适配层：`chat-main`
3. 客户端产品层：`openim-electron-demo`

总体原则如下：

1. 第一阶段不深改 OpenIM 内核 `group`、`conversation`、`message` 的核心 proto、RPC、表名。
2. 第一阶段优先在 `chat-main` 和 `electron` 完成业务命名、接口封装和页面替换。
3. 聊天室能力优先用“群组能力 + 业务适配层”实现，避免一开始就重写 IM 内核。
4. 对已经符合需求的能力，不做结构性重构，只补测试、约束和产品化细节。
5. 对当前缺失但 SDK 已支持的能力，优先补客户端入口和渲染。
6. 对当前连服务端接口都缺失的能力，先补 `open-im-server`，再补 `chat-main` 和 `electron`。

## 4. 范围划分

本次总方案包含以下六大范围：

1. 消息能力改造
2. 聊天室能力改造
3. 登录注册与账号能力改造
4. 权限、角色、通知和业务规则改造
5. Electron 客户端产品改造
6. 部署、配置、测试和文档改造

## 5. 改造方式总览

### 5.1 `open-im-server` 负责的内容

`open-im-server` 只承担 IM 内核职责，建议承担以下改动：

1. 补齐底层消息类型映射缺口。
2. 补充需要下沉到内核层的状态和权限能力。
3. 为 `chat-main` 提供稳定、可复用的原子 API。
4. 保持与 OpenIM 上游兼容，不在第一阶段深改核心模型名称。

### 5.2 `chat-main` 负责的内容

`chat-main` 作为业务适配层，建议承担以下改动：

1. 对外提供“聊天室”业务 API。
2. 承担群组到聊天室的命名和规则映射。
3. 增加聊天室扩展字段、状态机、黑名单、游客规则等业务能力。
4. 对登录注册、验证码、本地测试模式、业务通知做统一封装。

### 5.3 `openim-electron-demo` 负责的内容

Electron 客户端建议承担以下改动：

1. 对用户可见的命名全部改成目标产品术语。
2. 落地所有需求中要求的消息发送入口、消息渲染和管理页面。
3. 将当前原生“群聊产品”改造成“聊天室产品”。
4. 支持 `dev/main` 两套环境配置和安装包输出。
